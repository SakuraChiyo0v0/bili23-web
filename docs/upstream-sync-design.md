# bili23-web 上游同步机制设计（AI 移植 + 提醒 + 验收闭环）

日期：2026-09-03 · 状态：设计稿（尚未实施，未改任何代码）

## 一、结论先行

下游 `bili23-web` 是对上游 `ScottSloan/Bili23-Downloader`（Python + PySide6 桌面版，当前基准 v2.15.0）的 **1:1 TypeScript Web 重写**。两边语言、仓库结构、代码完全不同，因此：

- **不能用 git merge / rebase 做同步**——没有共同代码，merge 要么清空重写成果，要么什么都合不进来；
- **同步的正确对象是"上游行为"而不是"上游代码"**——每次上游发布一个新版本，就把它当作一份"行为变更单"，逐条评估并移植到对应的 TS 模块；
- 为保证"既有上游最新功能、又是重写后的功能"，机制必须满足三个能力：
  1. **自动检测 + 提醒**：上游出新版本时，下游能自动感知并收到提醒；
  2. **AI 介入的移植**：把上游 diff 转成可交给 AI（Codex）执行的移植任务书，AI 产出 TS 实现草案，人来审；
  3. **可观测的验收（"显测"）**：每个上游版本对应一条可勾选的验收清单 + 一张公开的状态追踪表，任何人（包括未来的你）都能回答"上游某功能有没有跟进来、为什么没跟进"。

> 说明：你提到的"显测"在本设计中按"可显式验证/观测的验收闭环"理解。若你的本意不同（例如希望有自动化测试或定期报告），见文末"待确认问题"。

## 二、为什么 git 同步对重写项目无效

| 方案 | 为什么不行 |
| --- | --- |
| 定期 merge 上游 main 到下游 main | 无共同祖先与共同代码，冲突无法解决；merge 结果没有意义 |
| GitHub "Sync fork" 按钮 | 只同步同名分支上的代码差异；下游是独立代码库，按钮没有可比对内容 |
| 把上游代码作为子目录 vendoring | 会污染重写仓库，且"重写后功能"与"上游代码"无法共存于同一逻辑单元 |
| 只保留上游 remote、不 merge | 可行，但**只是手段不是机制**——需要用本设计中的追踪与移植流程把它变成闭环 |

保留上游作为 `upstream` remote、拉取 tag，目的**只用于查阅与 diff**，绝不 merge 进 `main`。

## 三、总体机制：三层模型

```
上游发布新版本
      │
      ▼
┌─────────────────────────┐
│ ① 检测与提醒（自动化）    │  定时工作流查上游 releases/tags
│  · 发现比基准新的版本      │  → 自动生成"移植工单"（GitHub Issue）
│  · 开 Issue = 提醒        │  → 邮件/通知由 GitHub 负责
└─────────────────────────┘
      │ 移植工单（含 AI 任务书）
      ▼
┌─────────────────────────┐
│ ② AI 介入移植            │  把上游 diff + release notes 转成任务书
│  · Codex 读取任务书       │  → 产出 TS 草案 + 测试
│  · 人审阅、修正、合入      │  → 桌面专属特性按规则明确跳过
└─────────────────────────┘
      │ 完成
      ▼
┌─────────────────────────┐
│ ③ 验收与归档（可观测）    │  验收清单全部勾选
│  · 更新追踪表/基准        │  → 关闭 Issue、推进基准版本
│  · 留下"证据"            │  → 追踪表回答"功能是否已跟进"
└─────────────────────────┘
```

### 3.1 每个上游版本的状态机

| 状态（写中文名，代码中用英文） | 含义 | 如何进入 / 离开 |
| --- | --- | --- |
| 基准（`baseline`） | 当前已完整对照过的上游版本，是后续检测的起点 | 初始 v2.15.0；移植完成后人工更新状态文件 |
| 待移植（`open`） | 已检测到、已开移植工单，尚未处理 | 自动化检测发现新版本时自动进入 |
| 已移植（`ported`） | 行为已按重写原则移植进 TS 并验收通过 | 工单验收清单全勾选、关闭 Issue 时人工登记 |
| 已跳过（`skipped`） | 明确决定不移植（含原因），不静默丢失 | 人工登记，必须填写原因 |

**关键规则：`baseline` 只前进到"已处理（已移植或已跳过）"的版本**，防止漏掉中间版本。

## 四、自动化组件设计（待实施，本次只写设计）

以下均为**新增文件**，不修改任何现有代码。落地位置：`bili23-web` 仓库内。

| 文件 | 类型 | 职责 |
| --- | --- | --- |
| `.github/upstream-state.json` | 机器可读状态 | 记录上游仓库、当前基准版本、已处理版本清单 |
| `.github/scripts/upstream-sync.mjs` | Node 脚本（零依赖） | 检测、比对、分类、生成任务书、开/去重 Issue |
| `.github/workflows/upstream-sync.yml` | GitHub Actions | 定时 + 手动触发脚本 |
| `docs/upstream.md` | 人工追踪表 | 状态表 + 移植流程说明 + AI 任务书模板 + 验收标准（实施时新增） |
| 本文件 `docs/upstream-sync-design.md` | 设计文档 | 机制说明（即本文） |

### 4.1 状态文件 `.github/upstream-state.json`

```json
{
  "upstream": "ScottSloan/Bili23-Downloader",
  "baseline_tag": "v2.15.0",
  "processed": [
    { "tag": "v2.15.0", "status": "baseline", "handled_at": "2026-09-03", "note": "1:1 重写对标版本" }
  ]
}
```

- `baseline_tag`：检测起点，只能被人工推进到"已处理"版本；
- `processed`：历史决策记录，与 `docs/upstream.md` 表格互为备份（一个给程序读、一个给人读）。

### 4.2 定时工作流 `.github/workflows/upstream-sync.yml`

- **触发**：
  - 定时（建议每天 1 次，UTC `0 1 * * *`，即北京时间 09:00）；
  - 手动触发 `workflow_dispatch`（想立刻检查时用）。
- **权限**：`contents: read`、`issues: write`（只需读代码、写 Issue，不需要写代码）。
- **步骤**：checkout → 安装 Node（仓库引擎要求 ≥20）→ 运行 `upstream-sync.mjs --create-issues`。
- **产物**：每个新版本一个 Issue（label：`upstream-sync`）。

### 4.3 同步脚本 `.github/scripts/upstream-sync.mjs`

零依赖 Node 脚本（用内置 `fetch`，Node ≥20），可在 GitHub Actions 里跑，也可本地跑。逻辑：

1. 读取状态文件得到 `baseline_tag`；
2. 调 GitHub API 获取上游 releases（跳过 draft，预发布按普通版本参与比较，tag 无法解析时用发布时间排序兜底）；
3. 找出所有"比基准新"的版本；
4. 对每个新版本调 **Compare API**（`/repos/{上游}/compare/{baseline}...{tag}`）拿到变更文件与 commit 列表，不依赖本地仓库存有上游历史；
5. 用**尽力而为（best-effort）的分类表**初筛影响面：
   - 变更文件路径 → 对应 TS 模块（复用 `docs/design.md` 的模块映射）；
   - 命中桌面专属特征（GUI/托盘/剪贴板/窗口等）→ 标记"跳过候选"；
   - 命中网络/签名/解析相关 → 标记"接口风险，需实测"；
   - 分类只做初筛提示，最终判断归人/AI；
6. 生成"移植工单"正文（结构见 4.4），去重后创建 Issue（去重规则：存在同 label 且标题含该版本号的 open Issue 则跳过）；
7. Issue 的 label 不存在时先创建。

命令行模式（本地验证用）：
- `node .github/scripts/upstream-sync.mjs --check`：只打印报告，不改任何东西；
- `node .github/scripts/upstream-sync.mjs --create-issues`：检测 + 开 Issue（需要 `GITHUB_TOKEN`）。

### 4.4 移植工单（GitHub Issue）正文结构

标题：`[Upstream Sync] v2.16.0 → 移植评估`（版本号随实际变化）。

正文模板（每个新版本自动生成，字段已填好）：

```markdown
## 上游新版本：v2.16.0
- 上游：ScottSloan/Bili23-Downloader
- 发布时间 / 链接
- 相对基准 v2.15.0 的 diff 链接（Compare API / compare 页面）

## 上游 Release Notes（原文）

## 变更文件初筛（best-effort，需人工/AI 复核）
| 上游文件 | 推测影响 TS 模块 | 建议 |
|---|---|---|

## 建议动作
- [ ] 待分类：哪些需要移植、哪些是桌面专属可跳过

## 验收清单（全部勾选才可关闭）
- [ ] 已阅读 release notes 与 diff
- [ ] 已按 docs/design.md 映射确认影响模块
- [ ] AI 草案已由人审阅通过
- [ ] 移植代码 + 对应测试已合入
- [ ] `pnpm check`（typecheck + test + build）通过
- [ ] 涉及接口/解析的改动已完成一次真实冒烟下载验证
- [ ] 已更新 docs/upstream.md 状态表
- [ ] 已推进 .github/upstream-state.json 的 baseline 并提交
```

**关闭 Issue 即表示该版本验收完成**，与"推进 baseline"绑定，保证可观测。

## 五、AI 介入的移植流程（L2）

脚本只负责"检测 + 提醒 + 给材料"，**实际的代码改写由 AI（Codex）执行、人来验收**，这是对重写项目唯一现实的路径。

1. **触发**：上游新版本产生 Issue（提醒）后，把该 Issue 内容作为任务来源；
2. **任务书**：Issue 正文已含"上游 diff + release notes + 影响模块初筛 + 验收清单"，直接可交给 Codex；
3. **执行**：在 `bili23-web` 工作区对 Codex 下达任务（模板见 `docs/upstream.md`），约束包括：
   - 只移植上游的**行为变更**，代码必须按 TS 重写风格实现，不复制 Python 代码；
   - 遵守 `docs/design.md` 的"非目标"（桌面专属功能如托盘/剪贴板/短信登录 → 明确跳过并登记原因）；
   - 新增或修改的引擎行为必须带单元测试；
   - 禁止改动与本次上游版本无关的代码（范围纪律）。
4. **验收**：AI 完成草案 → 人审阅 → 按 4.4 验收清单逐项验证 → 合入并关闭 Issue、推进 baseline。

> 为什么不让 Actions 全自动改代码：上游 diff 转 TS 的准确性无法用机器保证，B 站接口类改动必须真实跑下载验证。AI 参与度停留在"草案 + 人审"是安全边界，不建议突破。

## 六、提醒机制

| 层级 | 机制 | 说明 |
| --- | --- | --- |
| 主提醒 | 定时工作流开 Issue | 仓库有活动即触发 GitHub 通知（邮件/App）；Issue 即"待办卡片" |
| 兜底 | 手动触发 | 想立刻检查时在 Actions 页面点 `Run workflow` |
| 可选的升级 | 长时间未处理的工单提醒 | 超过 N 天未关闭的 `upstream-sync` Issue，下次运行时评论提醒一次（默认不做，需要再开） |
| 可选的外挂 | Codex 自动化（cron） | 若希望"上游更新 → 自动唤起本地 Codex 移植"，可作为二期外挂；不属于本仓库代码，需单独确认 |

## 七、验收与可观测性（保证"既有上游功能、又是重写"）

"保证"不靠承诺，靠**可查证据**：

1. **追踪表即证据**：`docs/upstream.md` 里每个上游版本一行，状态只允许 `baseline / open / ported / skipped`，`skipped` 必须带原因；
2. **工单即验收单**：Issue 的验收清单全勾选才允许关闭；关闭才允许推进 baseline；
3. **代码即证据**：移植行为必须有引擎单测；接口/解析类改动要求一次真实冒烟下载（Web 或 engine CLI 均可），结果记录在 Issue 评论里；
4. **可回答的问题**：任意时刻都能回答——
   - 上游最新版是多少？→ 状态文件 baseline + 追踪表；
   - 某个新功能跟进了吗？→ 追踪表该行状态；
   - 为什么某功能没有？→ `skipped` 的原因列，或 `open` 表示还没轮到。

## 八、边界与失败处理

| 场景 | 处理 |
| --- | --- |
| 上游 tag 命名不统一（`v2.16.0` / `2.16.0` 等） | 解析前导数字版本；解析失败退化为按发布时间排序 |
| 上游发布 draft / 频繁改 tag | 跳过 draft；以 Compare API 失败时仅用 release notes |
| API rate limit | 脚本优先使用 `GITHUB_TOKEN`（5000/h）；本地 `--check` 无 token 时给明确提示 |
| 同一版本重复检测 | 以"存在 open 的同版本 Issue"去重，不重复打扰 |
| 一次漏掉多个版本 | 每个新版本独立 Issue，各自走状态机，不允许跳版本推进 baseline |
| 上游接口变更（B 站侧） | 分类标记"接口风险"，验收强制要求真实冒烟 |
